# ZK Voting

An experiment with [zero knowledge proofs](https://ethereum.org/en/zero-knowledge-proofs/). Zero-knowledge proofs are mathematical techniques used to prove the authenticity of information without revealing any additional information beyond what is necessary. They are a powerful tool for ensuring privacy and security in applications such as digital identity, blockchain, and cryptography.

This application allows registered voters to anonymously vote in any user-created poll. It showcases how zero knowledge proofs can allow for secure, secret voting, which is often desirable in elections to avoid any potential repercussions that might arise from others knowing the outcome of how someone voted. In this application, a user can prove they are a certain registered voter without revealing what their vote is.

Under the hood, the application uses two contracts: a Verifier contract, which is auto generated from a hardhat plugin (config in `hardhat.config.js`) that compiles circom circuits into solidity (in this case, the `add2Tree` and `proveInTree` circuits), and a ZKVoting contract, which imports the above functions from the Verifier contract.

For the voting process, a special kind of [merkle tree](https://en.wikipedia.org/wiki/Merkle_tree) is used called a sparse merkle tree (SMT). Merkle trees allow the linking of a set of data to a unique hash value. A sparse Merkle tree is like a standard Merkle tree, except the contained data is indexed, and each datapoint is placed at the leaf that corresponds to that datapoint’s index. In this case, when a user registers to vote, their "voter id" (index in the merkle tree) is a hash of their password. In order to prove they're the registered voter they say they are, they use a hash of their password so they don't need to reveal what their password actually is.

# Add2Tree Circuit

The `add2Tree.circom` circuit is used to add the voters secret to the merkle tree. This circuit uses the [iden3 smtprocessor](https://github.com/iden3/circomlib/blob/master/circuits/smt/smtprocessor.circom) circuit to verify inserts into the Sparse Merkle tree.

### Inputs

`oldRoot`: the previous root of the merkle tree. The root of our tree will be recorded within our smart contract.

`newKey`: the index at which the secret is added to the merkle tree. The next key will be enforced by our smart contract.

`newValue`: the value that will be recorded at the index defined above. It should be a hash of a secret and the wallet address. Our smart contract will record this value so others can reconstruct the merkle tree.

`oldKey`: the other index needed to reconstruct the merkle tree.

`oldValue`: the value that has been recorded at the index defined above.

`siblings`: an array of the intermediate hashes up to the root of the merkle tree. This input is private to save space, not out of necessity.

<br/>

# ProveInTree Circuit

This circuit proves we know a secret contained in the merkle tree, without revealing what the secret is. This circuit uses the [iden3 smtverifier](https://github.com/iden3/circomlib/blob/master/circuits/smt/smtverifier.circom) circuit to verify the secret and nullifier (wallet address) are a leaf on our merkle tree. This prevents duplicate or fraudelent voting.

### Inputs

`root`: the current root of the merkle tree. This is the only public signal in this circuit and will be enforced with our smart contract.

`key`: the index at which we prove our secret resides.

`secret`: voters secret that is not revealed.

`nullifier`: another secret number we use to hash our secret against, which is the users wallet address. We include this signal to make this circuit more extensible, but this can be modified for more anonymity.

`siblings`: an array of the intermediate hashes up to the root of the merkle tree. This input is private as we do not want to reveal the path to our secret, that would give away our identity.

<br/>

The `secret` and `nullifier` signals are hashed using a `poseidon` component (from [iden3 poseidon circuit](https://github.com/iden3/circomlib/blob/master/circuits/poseidon.circom), a hash function for Zero-Knowledge Proof Systems).
If all the inputs are correct (correct wallet, correct key (voter id), and correct secret), a valid proof is produced.

# Smart Contracts

### `Verifier.sol`

This contract was generated by the [hardhat-circom plugin](https://github.com/projectsophon/hardhat-circom) along with the template in `hardhat.config.js`, which combines the multiple steps of the [Circom](https://github.com/iden3/circom) & [SnarkJS](https://github.com/iden3/snarkjs) workflow. By providing configuration with a Phase 1 Powers of Tau and circuits, it compiles the circuits, applies the final beacon, outputs the wasm and zkey files, and generates and outputs a contract

### `ZKVoting.sol`

### **addLeaf**

```
 function addLeaf(
        uint[2] memory a,
        uint[2][2] memory b,
        uint[2] memory c,
        uint[6] memory input
    ) external {
        require(input[1] == root, "addLeaf: Invalid Root");
        require(input[2] == nextKey, "addLeaf: Invalid Key");
        require(
            registeredAddress[msg.sender] == false,
            "addLeaf: Wallet already registered"
        );
        require(
            Verifier.verifyAdd2TreeProof(a, b, c, input) == true,
            "addLeaf: Invalid Proof"
        );

        leafValues.push(input[3]);
        nextKey = leafValues.length;
        root = input[0];
        registeredAddress[msg.sender] = true;

        emit AddLeaf(input[2], input[3], input[1]);
    }
```

To register a voter (add a leaf to the merkle tree), a proof is created client-side with snarkjs and pre-generated zkey and wasm output from hardhat-circom (done in NextJS serverless function server-side). Outputs include the proof and public signals needed to send to the contract. The output data is then parsed to correct solidity format to send to the contract, and then the `addLeaf` function above is called. In order to correctly insert a new leaf into the merkle tree, the correct root hash, key (next index in tree), and valid proof must be passed. If all these checks pass, a new leaf is added to the tree, and the key and root are updated. Lastly, the wallet address of the voter is registed in a solidity mapping. In the future an update will be made to encrypt the user's wallet address. When a user registers to vote, their wallet address can still be seen through the transaction, so steps should be made in the future to obfuscate their address (batching, mixing, etc).

### **proveMembership**

```
function proveMembership(
        uint[2] memory a,
        uint[2][2] memory b,
        uint[2] memory c,
        uint[3] memory input,
        bool vote // bool determining if we will vote positively or negatively towards the voteId provided by the proof
    ) external returns (bool r) {
        require(voteLogged[input[0]] != true, "proveMembership: Vote Logged");
        require(
            voteDeadline[input[2]] > block.timestamp,
            "proveMembership: Deadline Passed"
        );
        require(input[1] == root, "proveMembership: Invalid Root");

        r = Verifier.verifyProveInTreeProof(a, b, c, input);
        require(r == true, "proveMembership: Invalid Proof");

        voteLogged[input[0]] = true;

        if (vote == true) {
            positiveVoteResult[input[2]] += 1;
        } else {
            negativeVoteResult[input[2]] += 1;
        }
    }
```

The `proveMembership` function is quite similar to the `addLeaf` function in its parameters. The proof is generated client-side, however the proof is also verified using the pre-generated zkey and proof outputs to ensure a valid proof is being sent to the contract to prove (in an effort to save the user gas on a transaction that would fail). The contract ensures the voter hasn't voter already, the deadline hasn't passed, and that a valid hash root for the tree was provided. The contract then verifies the proof, and if passed, the user's vote is logged to a solidity mapping. Although you can see a voter submit a transaction when voting, zk prevents the the user's vote choice from being revealed. The first vote to be cast is not anonymous, as the transaction could be cross referenced with the voting tally for a proposal, but as votes increase, the degree of anonymity increases. As stated above, efforts should be made here to batch or mix votes before they are submitted.

`yarn run deploy --network goerli`

# Flaws

- When voting, you can see when an adress voted via the on chain transaction. If it's early on in the voting cycle, could possibly correlate voting times with voting
- Someone may call createVote() with a deadline one second above the current block timestamp, then in the same transaction vote for their own proposal, preventing anybody else from voting on their proposal
- When an address proves its membership, its anonymity is limited to the secrets held in the tree at the time of proving. The more registered secrets, the better the anonymity will be
